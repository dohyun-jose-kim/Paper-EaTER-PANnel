# User choices and remaining design decisions

Status: Draft for user review.

Updated: 2026-11-13.

Project version: `v0.2.1`.

## Purpose and use

This document separates user choices and intended product behavior from remaining design decisions for `PAPER-LLM-read`. Read it with [Design status](design-status.md) and the [development README](../readme-dev-v0.1.md).

The product must provide defaults and let users change supported settings. Model selection and combinations, execution count, concurrency, conflict-resolution policy, and all three deliverable modes are established user choices. Their exact defaults, supported ranges, combination constraints, and implementation mechanisms still need design. A user's choice for a task is not an unresolved product design decision.

A GUI is required to help users understand these variables, available choices, and the effects of combinations. It must support informed, active use of defaults and settings. Screen implementation is not limited to static HTML or a specific language or framework. React, TypeScript, and other suitable technologies may be used. Frontend technology and execution-layer technology can be selected separately.

The table does not define an implementation schedule, schema, interface, or evaluation protocol. Intended behavior is not a claim of completed implementation. Internal architecture, security policies, and acceptance criteria are not automatically user settings. The user can change the order and priority of the remaining design discussions. No previous project's architecture or evaluation boundary is a requirement here.

## User choices and design work

| Design topic | User choice and intended behavior | Remaining design decisions |
|---|---|---|
| User workflow and final deliverable | Users choose among all three required modes: a transcript with source images, a source-aware reading workflow, and both together. These modes are support requirements, not competing proposals for a single product direction. | Default mode; detailed behavior and handoff mechanisms for each mode; when to return to the source; saved artifacts, interactive work, and reuse. Use representative tasks and receiving applications or models to determine these details. |
| Models and access changes | Users select a model or supported combination. The wrapper must accommodate changes in models and CLI/API access. The GUI must help users understand relevant capability differences. | Supported model catalog and combinations; defaults; access paths; input capabilities; behavior when models become unavailable or interfaces change. Use capability evidence and compatibility needs to define constraints. |
| Execution count and model combinations | Users set execution count and select supported model combinations. The GUI must explain their meaning and relationship. | Unit of work: region, page, section, document, or task; count range and default; supported combinations; cross-unit context. Use error types, evidence of benefit, latency, usage, and cost to define the choices. |
| Concurrency | Users set how many executions may run at the same time within supported limits. This choice is independent of execution count. | Default and allowable limits; dependencies between operations; resource and provider constraints; treatment of pending work; explanations of responsiveness and usage effects. |
| Comparison and conflict resolution | Users select a supported conflict-resolution policy. The GUI must explain what each policy does and how unresolved content is represented. | Policy set and default; comparison unit; source checks and human review; treatment of agreement, disagreement, unreadable content, omissions, and unreviewed results. Determine whether voting is useful for any defined case from error consequences and evidence. |
| PDF, text, and image input delivery | The workflow must establish what text and images a model actually receives and the scope it inspects. Which input controls users need remains a design question. A local file path alone does not establish delivery. | Input paths and preprocessing; evidence of received content; document context and page boundaries; input limits and effects of extraction or image scaling. Use access-path capabilities and representative layouts to decide. |
| Images, captions, body text, and source locations | Users need to connect results to the relevant source content. Navigation and inspection behavior must be designed; underlying source relationships are not automatically configurable settings. | Source-location precision; multi-panel figures, tables, cross-references, and page-spanning content; use of images, text, or both. Use intended tasks and consumer needs. No image or table-content exclusion is inherited from earlier work. |
| Internal representation and handoff format | Each selected deliverable mode must reach its intended consumer with the required text, images, and source links. Whether users choose among export formats remains to be designed. | Internal representation; supported JSON, HTML, Markdown, image, or combined handoffs; image delivery; equations and tables; portability and reuse. No schema is selected. Handoff format is separate from GUI implementation technology. |
| Execution state, failure, and recovery | Users need understandable execution status and behavior for failure, cancellation, interruption, resumption, and reuse. The specific controls remain to be designed. | State model and status display; distinction between failed, incomplete, unreadable, uncertain, and unreviewed results; recovery and retry policy; reuse conditions; provenance for inputs, models, settings, outputs, and review. Use failure scenarios, audit needs, retention, and cost limits. |
| Authentication, permissions, and secrets | Users need appropriate authentication and permission interactions. Keep secrets out of tracked files. Security policies are not automatically user settings. | CLI/API authentication; required permissions; `.env` variables and loading; transmission and logging; GUI handling of document content, HTML, links, and active content. Use source sensitivity, service data handling, and rendering requirements. `.gitignore` alone does not settle security. |
| Implementation technology and GUI | Provide a GUI for informed, active choice. Users must understand defaults, variables, supported combinations, and their effects. Implementation technology is an engineering decision, not a user setting. | Layout, explanations, controls, and any complementary CLI role; frontend and execution-layer technologies; integration, deployment, and maintenance needs. React, TypeScript, and other suitable frontend technologies are allowed. Go, Rust, and Python remain execution-layer candidates. No framework is selected. |
| Subscription usage and API costs | Users need to understand usage and cost implications of their choices. Existing subscriptions are the initial preference; API access remains possible. Specific budget and usage controls remain to be designed. | Reporting, limits, defaults, and controls before additional usage or charges; available access and billing terms; workload and budget expectations. Do not assume automatic paid fallback or convert subscription use to API cost without a basis. |
| Fidelity, reproducibility, and traceability | The product must be assessed for preservation of source information, repeat consistency, and source links. Acceptance criteria are product design decisions, not automatically user settings. | Reference and review methods; representative samples across supported modes; consequential errors; handling of uncertainty; thresholds; detection of omissions and newly introduced distortions. No sample size, repeat count, or pass criterion is selected. |

## Decision records and next review

When a design question is resolved, record the decision and its basis in [Design status](design-status.md). Update this table to show any remaining design work. Keep supported choices and defaults distinct from the values a user selects for a task. Selecting a default does not remove user choice. Selecting one variable does not resolve related variables.

Fidelity means preserving the intended source information. Reproducibility concerns consistency under stated conditions. Traceability concerns the ability to connect a result to its source and processing history. Agreement between repeated outputs does not establish fidelity. Observing no errors in a sample does not guarantee error-free delivery.

The next review should identify missing topics, incorrect status assignments, and any confusion between user controls and internal design. The user does not need to resolve every remaining detail before accepting these documents as an accurate record of the current design discussion.
